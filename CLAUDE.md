# Tethys

Desktop app for managing multiple Claude Code CLI sessions in parallel across git worktrees. Each "workspace" bundles N worktrees (one per repo) plus the one Claude session running inside them, with "your turn" notifications driven by Claude Code hooks.

**This is a personal tool built for Ryan.** No multi-user, no cross-platform, no distribution plans. macOS-only for the foreseeable future — feel free to take macOS-specific paths, shell invocations, or Tauri features without guarding them.

This repo has no branches — work directly on `main` and commit there. Don't create feature branches or PRs.

## Stack

Tauri 2.x shell · Rust core (`src-tauri/`) · React + TypeScript frontend (`src/`) · xterm.js (DOM renderer) for terminal rendering · `portable-pty` for PTY spawning · JSON file persistence (no SQLite) · `tethys-hook` companion binary (`crates/tethys-hook/`) that forwards Claude Code hooks over a Unix socket · `tethys-mcp` companion binary (`crates/tethys-mcp/`, built on the `rmcp` SDK) that gives each session five MCP tools: handing work off to a new workspace, linking a PR to the current one, adding repos to it, asking for a higher memory budget, leaving Shipping, and reporting progress.

## Running

```
pnpm tauri dev
```

State lives at `~/Library/Application Support/app.tethys.dev/` (`state.json`, `logs/`, `repos.toml`, auto-generated `repos.schema.json`, `hook.sock`, `mcp.sock`).

Tethys writes its hook entries into `~/.claude/settings.json` on every boot (keyed by `description: "Tethys session monitor"`). They're idempotent — safe to leave across reinstalls.

It also generates a `CLAUDE.md` at each workspace root (`workspace_doc.rs`) explaining the worktree layout and telling sessions to ask for a missing repo rather than reading some other checkout. Rewritten on create, on repo-add, and at every boot. Claude Code reads CLAUDE.md from every parent dir, so the root file also applies to a session running inside one repo's worktree.

The prose lives in `repos.toml`, not in Rust: `[workspace_doc].body` (with `{branch}` / `{repo_list}` / `{available_repos}` / `{workspace_root}` / `{clone_dir}` placeholders) falling back to `DEFAULT_BODY`, plus per-repo `claude_notes`. Rust owns only the marker line and the "Repo notes" section.

## The workspace's session

A workspace runs **one** agent session — `Workspace::session` is an `Option`, not a list. Several used to be allowed, each with its own tab in a chip bar above the terminal, its own cwd, a per-session binary override and a hidden flag; in practice every workspace ran exactly one, so the tab bar and everything behind it went. `Store::load` folds an old `sessions` list down to the newest visible entry with a saved conversation (`migrate_sessions`), lifts its binary override onto the workspace, and leaves the rest for the boot-time orphan reap to kill.

Where it runs is decided once, by `Workspace::session_cwd`: the workspace root, whatever the repo count. A one-repo workspace used to start inside that repo's worktree so the repo's own `CLAUDE.md` and settings were the session's project, but that made adding a second repo an awkward half-move — the session stayed below the root while its new sibling sat above it, reachable only by a path out of the tree the generated doc describes. The root is the honest answer to where the work happens, and a repo's own `CLAUDE.md` is still picked up on the way into its subtree. An existing session keeps its cwd through every restart, so sessions started under the old rule stay in their worktree; only new ones move.

Every way of putting the session on screen is one function, `sessions::open_session`, and one command, `start_agent_session`. It does the least that works, in order: return the running handle, reattach a tmux pane that outlived the app, resume a conversation that is actually on disk (`transcript_is_resumable` — an empty transcript would fail with "No conversation found"), else start fresh. Start, Resume and Reconnect in the UI are all this call; the frontend auto-fires it for a dormant session with a saved conversation. A fresh spawn or a resume replaces the persisted meta and drops the old handle from the supervisor, since the tmux session name *is* the session id and a new tmux session means a new id.

A workspace still provisioning shows an **Initial prompt** box; whatever is typed there is pasted into the session — bracketed paste, not submitted — once the agent's TUI is up. "Up" is read off the PTY stream: `PtyProcess` watches the live bytes for the program turning bracketed paste on (`ESC[?2004h`) and surfaces it as `SessionInfo::tui_ready`. It used to key off the SessionStart hook, which is right for Claude but wrong for codex — codex fires SessionStart at its *first turn*, not at startup, so the draft arrived in the composer after the user had already sent a message. Both TUIs enable bracketed paste as part of drawing their first frame, and tmux forwards the mode change for the active pane, so the signal is agent-neutral and needs no hook at all.

`switch_agent` is the one way to change agent or binary after creation: it writes `Workspace::agent` and `agent_binary`, kills the tmux session so the reattach step can't win, and calls `open_session`, which resumes if it can. It lives in the workspace header as a "run with" dropdown. Switching *across* agents drops the session meta first, since neither CLI can read the other's transcript — that switch necessarily starts a fresh conversation.

A session nobody has touched in **24 hours is closed** (`idle.rs`): its tmux session is killed, which is all closing is — the conversation stays on disk and Resume picks it up. "Touched" is a keystroke through `send_input` or any turn hook the session fires, so an agent grinding through a long turn counts as active; the timestamp is `AgentSessionMeta::last_active_at`, persisted because `prewarm_live_sessions` reattaches every pane at boot and tmux's own `session_activity` would reset on every restart. Keystrokes land in an in-memory map on the supervisor and are folded into the store by the 10-minute sweep, not written per key. A session sitting in `Working` is never closed, since a tool call can run for hours without a hook. Because the killed session keeps its supervisor handle, the frontend shows Resume rather than auto-reopening it — until the next restart, when visiting the workspace resumes it like any dormant one.

Closing a session doesn't take everything it started with it. A dev server backgrounded with `nohup`, or a test run orphaned by a timed-out tool call, reparents to launchd and keeps running — the first ones found were two 12-day-old `stt-review` servers at ~1.5GB each. These are **strays**, and `strays.rs` kills them on a 10-minute sweep. No process tree leads from a stray back to its session, but its environment does: tmux starts each session with `TETHYS_SESSION_ID` and `TETHYS_SPAWN_TOKEN`, every descendant inherits them through any amount of detaching, and macOS lets a process read the environment of another it owns. So a stray is simply a process whose tag names no live tmux session — no heuristics about CPU, age or memory. Either tag counts as live, since sessions from before `TETHYS_SESSION_ID` carry only the token, and codex may filter `*TOKEN*` vars out of the commands it runs.

Its safeguards matter more than its rule. The sweep is skipped outright if tmux can't list every session and its environment, since a session missing from the answer would read as dead. The process snapshot is taken *before* the session list, so a session started in between has nothing in the snapshot to lose. Tethys, its ancestors and its children are spared, and so is anything sharing Tethys's own tags — `pnpm tauri dev` run from inside a session puts the whole dev tree under that session's tag. tmux and `memwatch.sh`, and everything under them, are spared by name, because both outlive the Tethys that started them and could carry the tag of a session that has since died; killing the tmux server would take every session with it. A kill is SIGTERM, then SIGKILL after 10 seconds, and each pid is re-read against its start time before either signal so a reused pid is left alone.

### Memory budget

macOS has no cgroups and enforces no memory limit on a process or a tree — `ulimit -v` is refused, `RLIMIT_RSS` ignored — so a test run that grows past what the machine has doesn't fail, it swaps everything to a standstill. `budget.rs` is the limit macOS won't provide: every 3 seconds it sums the footprint of every process carrying a session's `TETHYS_SESSION_ID`, and a session over its **budget** (8 GB; `TETHYS_MEM_BUDGET` takes a number of GB or `off`) loses its biggest job. It's the same tag the stray sweep reads, so it sees Python, Node, anything, with no cooperation from the agent or the repo's test config.

The agent CLI itself — the tmux pane's process — is neither counted nor killed; the budget is for what the agent *ran*. A **job** is a subtree hanging off the agent (one Bash tool call, a background task, an MCP server) or one that detached from it, and a job goes whole, SIGTERM then SIGKILL after 5 seconds, so a test runner and its workers die together. One job per session per sweep: the next sweep sees what that freed. Memory is `ri_phys_footprint`, the Activity Monitor number, because RSS leaves out compressed pages and understates exactly when memory is short. Processes sharing Tethys's own tags are spared, as with strays. The environment is read once per process — `sysinfo`'s `OnlyIfNotSet` on a `System` kept across sweeps — so a sweep is ~12ms.

The agent is **told why**, because an unexplained exit 143 reads as a flaky test and gets rerun. The notice is recorded *before* the signal, and the killed command's own `PostToolUse` or `PostToolUseFailure` hook carries it back as `additionalContext`: `tethys-hook` waits up to 500ms for a reply on those events and on `UserPromptSubmit` (`tethys_hook::reply_event_name`), and stays fire-and-forget on every other. `PostToolUseFailure` is registered only for this — it also fires for a tool the user interrupted, so it touches no turn state. Codex sessions are killed the same way but not told: nobody has checked whether codex's hooks can return context.

An agent that genuinely needs more calls `mcp__tethys__request_memory_budget` (GB, minutes up to 480, a reason). Only Ryan can grant it: the call **waits** — up to 30 minutes, then it's refused — while the workspace's sidebar dot lights and an Approve/Deny banner sits above its terminal. The dot is OR'd in on the frontend rather than set as turn state, because the agent is mid-tool-call and the Claude probe would correct a `WaitingInput` back to `Working` within 2 seconds. A grant raises that session's budget, never lowers it, and lapses on its own; grants and pending requests live in memory and are gone after a restart, which is the safe direction.

Deliberately absent: a machine-wide floor (killing the biggest session when free memory or swap says the whole machine is in trouble even though no one session is over), anything inside OrbStack's VM (its own `memory_mib` is the guardrail there), a sidebar mark for a kill, and pausing instead of killing.

Deliberately absent: a second session, a session per agent, any way to start a fresh conversation while one exists (`/clear` inside the agent does that), the per-repo **scripts** (`[repo.scripts]` in `repos.toml`, the `dev` chip and its terminal — a stale table in your `repos.toml` is ignored, not an error), and per-session anything.

## Which agent runs

`Workspace::agent` is an enum — `Claude` or `Codex` — sitting beside `agent_binary`, which is the executable name (`claude`, `claude-hipaa`, `claude-unsafe`, `codex`). Two fields, one control: the header's "run with" dropdown lists `(agent, binary)` pairs. The kind is *stored*, never derived from the binary name, because it decides how hooks are installed, how a conversation resumes and how MCP is wired — none of which may hinge on how an executable happens to be spelled. `Store::load` reads the old `claude_binary` / `claude_session_id` keys through serde aliases, and an entry with no `agent` loads as Claude, which is what it was.

There is no agent abstraction, deliberately. `agent_cmd::build` is one function per agent because the two command lines share nothing but the binary and the trailing prompt, and a trait built against a sample of two would be shaped by neither. Everything else — worktrees, provisioning, PR tracking, folders, children, artifacts — is agent-agnostic and got nothing new.

Codex is configured entirely on its command line. It layers config from several files and `-c` is the highest-precedence layer, so Tethys writes nothing into `~/.codex/config.toml`: the user's config stays theirs, a session's whole configuration is visible in one command line, and a hand-run `codex` behaves like plain codex. That's the opposite of the `~/.claude/settings.json` hook install, which exists only because Claude Code hooks *can't* be passed per-invocation.

Four parts of the codex line carry reasoning worth keeping:

- **`--dangerously-bypass-hook-trust`.** A hook defined at spawn starts untrusted and *silently doesn't run*. The alternative is writing a `[hooks.state]` stanza per spawn, hashed over a command string that carries a fresh spawn token every time — an unbounded pile of dead entries in the user's global config. The flag's scope is the hooks on the command line Tethys just wrote.
- **`--sandbox workspace-write --ask-for-approval on-request`.** The faithful equivalent of plain `claude`: free in its own workspace, asks before anything else, and the ask surfaces as the sidebar's "your turn" dot via the `PermissionRequest` hook. Spelled out rather than left default because a worktree is an *untrusted project* to codex, and untrusted defaults to read-only.
- **`--add-dir <repo git dir>`**, one per repo. A worktree's real git dir lives under Tethys's data dir, outside the workspace root, so without these the sandbox permits reading the checkout but not one git command. The direct mirror of `claude_local::grant_git_dirs`.
- **`-c project_doc_fallback_filenames=["CLAUDE.md"]`.** Tethys generates one workspace doc and it's called `CLAUDE.md`; this points codex at the file that's there instead of generating a second under another name for the two to drift apart. It works because the session runs at the workspace root — codex's own `AGENTS.md` walk stops at the git root, which a workspace root is not, so the doc is read as cwd's rather than found by walking.

Hooks were the good surprise: codex has twelve, enabled by default, definable inline with `-c hooks.<Event>=[…]`. A handler's `command` is a **shell string, not an argv array** — codex rejects the array form while *loading config*, so getting it wrong doesn't degrade hooks, it kills the session before the TUI starts, and the pane exits 0 with the error scrolled away. Each word is single-quoted on the way in (`shell_word`). Seven are registered (`CODEX_HOOK_EVENTS`), mapping onto the existing turn state machine, which needed no changes — it was already agent-neutral. Codex has no `Notification`, but `PermissionRequest` covers the same ground and Tethys already understood it from Claude; `Interrupt` is new and ends a turn like a `Stop`. `tethys-hook` stays one binary, since the two payloads are near-identical — it takes the spawn token as an *argument* for codex rather than an env var, because Tethys writes that command line itself and an argument can't be filtered out by a `shell_environment_policy`.

The probe backstop (`probe.rs`) stays Claude-only. It exists to heal Claude's session id after it rotates on compaction, and codex's is a stable UUIDv7. Codex sessions are *filtered out* of reconciliation rather than merely failing to match: a workspace switched from Claude to codex keeps its cwd, so a dead Claude probe would otherwise heal a Claude session id onto the codex session that replaced it.

Two things needed the escape hatches. Codex asks *"do you trust the contents of this directory?"* on the first run in any new directory, and every workspace is a new directory — so it would ask every time, on a screen nobody is watching when a handoff started the session. That one *cannot* be said on the command line: `-c projects."<dir>".trust_level="trusted"` parses and is accepted, and the prompt still appears, because the check reads persisted config rather than the session layer. So `codex_trust.rs` writes the stanza into `~/.codex/config.toml` with `toml_edit` (comments and formatting survive), under the same `flock` as the Claude hook install, and purge removes it again so the file doesn't collect one per workspace ever created. Keys are the *resolved* path — `/tmp` and `/private/tmp` are different projects to codex — resolved via the deepest existing ancestor so purge computes the same key after the worktree is gone. Trusting also lets codex load project-local `.codex/config.toml`, `.codex/hooks.json` and `.rules` out of the checkout, which is a real widening, and the same trust Tethys already extends by cloning the repo and pointing an agent at it.

The other one turned out not to be codex-specific at all. `PtyProcess::attach` handed a newly-mounted xterm.js the raw scrollback ring, and recorded output contains the *queries* a program asked the terminal at startup (`ESC[6n`, `ESC]11;?`, `ESC[c`, `ESC[>c`). A terminal answers a question whenever it reads one, so every workspace switch replayed those questions into a fresh emulator, which sent stale replies up the PTY into whatever the program was showing — in codex, `0;276;0c` typed into the composer. `scrollback::strip_queries` takes the queries out of the *replayed* copy only; live bytes stream through untouched, since a query asked now is one something is waiting on. A query renders nothing, so nothing is lost on screen.

The replay had the opposite problem too: it can lose things the terminal *needs*. tmux turns mouse reporting on when its client attaches and on a resize, never while output streams, so once a busy session has pushed 2MB through the ring the switch is gone, and a freshly mounted xterm keeps the wheel for its own buffer instead of sending it to tmux — scrolling dead until a window resize made tmux say it again. `scrollback::TermModes` watches the live stream for the DEC private modes that matter (mouse protocols, focus, bracketed paste, cursor keys and visibility — not the alternate screen) and `attach` re-asserts their last state after the replay.

Deliberately absent for codex: model selection (set `model` in `~/.codex/config.toml`), a third agent, per-agent terminal tuning, and any visual mark in the sidebar distinguishing a codex workspace.

## The session's MCP tools

Tethys renders an MCP config per session at spawn time — nothing on disk, either way. Claude gets `--mcp-config` (inline JSON) paired with `--allowed-tools` naming *every* tool, so no call can stall on a permission dialog nobody is watching; never `--strict-mcp-config`, which would cut the session off from every other MCP server. Codex gets the same server as `-c mcp_servers.tethys.…` overrides, with `tools.<t>.approval_mode="approve"` as its `--allowed-tools` equivalent. Both bake the identity into the server's `env` block. Six tools live behind it — `request_memory_budget` is covered under **Memory budget**, `leave_shipping` under **Shipping** and `set_progress` under **Children** — sharing one socket and told apart by the frame's `op` tag.

### Handoffs

A session can create a *new* workspace — a **handoff** — through `mcp__tethys__create_workspace`.

The calling workspace and session ids are baked into that config's `env` block, not passed as tool arguments — that's what makes the recorded `Origin` unforgeable. The new workspace inherits the caller's `claude_binary`, so work can't drift out of a `claude-hipaa` workspace by accident.

The tool returns as soon as the `Creating` draft is in state: provisioning runs in the background and the calling agent never hears how it went, so a failure shows up only as a `CreationFailed` row in the UI. With `as_child` the new workspace is the caller's child, and the caller is told when it's deleted (see **Children**). Every Tethys-spawned session gets the tool, including handoff-created ones — chains are possible and there is no concurrency cap yet.

### Linking a PR

`mcp__tethys__link_pr` points the *calling* workspace at a PR that already exists on GitHub — the only way to attach a PR by hand now that the header's attach dialog is gone (`github/attach.rs`). It takes a reference (`123`, `#123`, `owner/repo#123`, or a URL) and an optional `repo_key` for when the workspace spans several GitHub repos; the workspace itself comes from the config's `env` block, like the handoff origin, so an agent can only ever link to its own.

`record()` is a plain insert-or-refresh into the link's one PR list (see **Tracked PRs**), so linking a PR the poller already found is a refresh rather than a second chip. It reports back whether the PR turned out to be the one for the workspace's own branch — read off `head_branch`, not off where it was stored — so an agent can tell "I linked the PR I just opened" from "I linked somebody else's".

Deliberately absent: no creating or editing PRs (this records, it doesn't act on GitHub), no unlinking, and no linking to any workspace but the caller's.

### Adding repos

`mcp__tethys__add_repos` adds repos to the *calling* workspace — the agent-facing half of the "Add repo" picker, and the same function behind both (`provision::add_repos`): same setup-queue slot, same commit-as-each-lands, same rollback of only the failing repo's worktree. The workspace comes from the `env` block, like the other two, so an agent can only ever grow its own.

Unlike a handoff, it **waits**. A handoff's result belongs to a session that doesn't exist yet; a repo added here is something the caller wants to use in its very next step, so the reply carries each worktree's path. That can mean minutes, which is why the codex line raises `tool_timeout_sec` from its 60-second default. Claude Code's own MCP timeout is already long enough. An interrupted call doesn't cancel the job: Tethys finishes it and only the reply is lost. That's why a repo the workspace already has is reported back with its path rather than refused, so an agent that retries gets an answer instead of an error. A partial failure names the repos that landed before it.

A codex session's sandbox can't write to the new repo's git dir until it restarts, because `--add-dir` is fixed at spawn. Claude's grant lives in the workspace-root `settings.local.json`, which an add extends.

Deliberately absent: no removing repos, no progress shown in the UI while an agent's add runs (the row updates when each repo lands), and no adding to any workspace but the caller's.

One trap worth remembering: Claude Code negotiates MCP protocol `2026-07-28`, which requires `ttlMs` on a `tools/list` reply. `rmcp`'s `with_all_items` omits it, and a reply without it is silently rejected and retried until the client reports "tools fetch failed". `tools_result()` sets it, and a test in `crates/tethys-mcp` holds it there.

## The setup queue

Provisioning runs **one workspace at a time** (`provision_queue.rs`). Asking for five at once used to start five clones and five `pnpm install`s on one machine, and a setup script that takes two minutes alone can run past its `setup_timeout_secs` when it's sharing the disk with four others — which isn't a slow workspace but a failed one, since a timeout rolls the whole thing back.

The gate is a one-permit tokio semaphore, so admission is FIFO: the first workspace you asked for is the first you can start working in, rather than all five landing together at the end. Every path that provisions takes it — the create dialog, adding a repo to an existing workspace, and a handoff — which is why it's shared state rather than a field on any one of them. It is not a tuning knob; a concurrency budget is a different feature.

A job that has to wait says so twice: a status line on its job channel, and `WorkspaceStatus::Queued` on its own row, so a sidebar full of pending rows can say which one the machine is actually building. `Queued` is a draft like `Creating` — same boot-time prune, no worktrees, nothing running.

Waiting also made "deleted while creating" an ordinary thing to do rather than a race, so `provision_workspace` re-checks `deleted_at` the moment it gets the slot and abandons the job before the first clone. The row is left `Queued`, not `CreationFailed`: it never failed, it was called off.

A job that can sit in the queue for minutes is a job nobody should have to watch, so **no provisioning log is a modal**. Adding a repo used to put one up, which froze the whole app — including every other workspace's session — behind a job that was often just waiting its turn. The invoke now lives in `App` (`addRepoRuns`, keyed by workspace id) with the channel writing straight into that map, so nothing has to stay mounted for the log to keep accumulating; the workspace's detail pane only *displays* the run it's handed, floated over the top-right of its session pane. It's the same shape `CreationRunner` has always had for `create_workspace`. Only the repo *picker* is still a modal, and only for as long as the choice takes; the popup's dismiss stays disabled until the job settles, since dismissing wouldn't stop it.

Deliberately absent: no persisted queue (quit with four waiting and they're gone, exactly like a workspace caught mid-provision), no priority, no way to reorder or cancel a queued job except by deleting the workspace, and no cap on how many can wait.

## Per-worktree env

Every worktree sits in a folder named after its repo (`<workspace>/nl-backend`), and Docker Compose names a project after the folder holding the compose file. So every workspace — and the main checkout — landed in one Compose project, sharing its postgres, volumes and built image. A `docker compose down -v` in one workspace deleted the main checkout's dev database on 2026-11-03.

A repo's `[repo.env]` table in `repos.toml` is the fix, and it's generic rather than Compose-aware: Tethys knows nothing about Docker. Each pair is upserted into the worktree's `.env` right after `copy_files` (a line for the same key, copied from the clone, is replaced rather than duplicated) and exported to the setup script. Values take `{repo}` and `{workspace}`, the latter the workspace folder lowercased with anything outside `a-z0-9_-` turned into `-`, since Compose rejects capitals and dots in a project name. nl-backend sets `COMPOSE_PROJECT_NAME = "{repo}-{workspace}"`.

A project per workspace means a pile of images and volumes per workspace, so a repo can also set a `teardown_script`, which purge runs in the worktree before removing it. Best-effort: a failure is logged and the purge carries on. It gets the same rendered env, and rendering depends only on the worktree path, so the teardown addresses this workspace's project even when the `.env` never had the line. That matters because existing workspaces weren't backfilled: a `docker compose down -v` that fell back to the folder name would delete the shared project all over again. nl-backend's teardown spells the project out with `-p "${COMPOSE_PROJECT_NAME:?}"` for the same reason.

Deliberately absent: a backfill of existing worktrees (their running stacks would be orphaned and their next run would start on an empty database), a teardown on provisioning rollback, and any isolation of nl-backend's fixed `container_name`s and host ports — so two workspaces still can't both `docker compose up`, though `docker compose run --rm django …` is fully isolated.

## Shipping

A workspace whose work is done can be put in **Shipping** (`shipping.rs`): its PRs only need approval, green CI and a merge, and Tethys shepherds them there instead of Ryan. It leaves the sidebar list for a grid of small tiles between the list and "New folder", one per workspace, coloured by the worst of its open Shipping PRs — green when approved, passing and conflict-free (or already in the merge queue), red with a struck-through eye when nobody has been asked to review it (it outranks everything else, being the one thing only Ryan can fix), yellow with an eye while it waits for review, yellow with the CI icon when CI fails, grey while CI runs. A child that leaves for the grid also shows as a small copy of its tile on its parent's row, since that's where Ryan looks for the work he handed out. The tile is the "your turn" signal for a Shipping workspace; the ordinary turn highlight doesn't apply, because most turns a Shipping session takes are ones Tethys started.

The state is `Workspace::shipment` — `None`, `Shipping { prs }`, or `Shipped`. **Shipping PRs** are the ones named when shipping (the context menu's Ship, which asks only when there's more than one open PR); every other tracked PR is ignored, stacks included. A workspace with no open PR can't ship.

The poller drives it. `apply_results` records each meaningful old → new status as a `StatusTransition`, and `shipping::react` runs in the same store write: a Shipping PR that just *went* conflicting, red, or out of the merge queue without merging queues a **Nudge** on the workspace, and `settle` moves on any workspace whose Shipping PRs are all closed. Edge-triggered on purpose — a PR that stays red isn't Nudged every 45 seconds, but a fix that goes red again is. Starting to ship treats current status as new, so a PR that's already red is Nudged straight away.

A Nudge goes through the same queue and inbox as child events, and names the fix: rebase for a conflict, `/monitor-ci` for red CI, find-fix-requeue for the merge queue. Every one also says the agent can call `mcp__tethys__leave_shipping` when something needs Ryan instead, which sets `shipment` back to `None`. Shipping sessions are the ones nobody is watching, so idle-close gets them first; `Shipper::wake` resumes the session before delivering, and a freshly spawned one picks the queue up at its SessionStart.

When every Shipping PR is closed, merged or not, the workspace is **Shipped** — its tile stays in the grid, solid green with the merge icon, waiting to be deleted — unless another of its PRs is still open, in which case it goes back to the list. Detaching every Shipping PR calls the shipment off. Ryan can take a workspace out of the grid from its context menu; typing into a Shipping session doesn't.

Deliberately absent: Nudges for codex (no inbox, so a codex workspace can ship but is never told anything), Nudges for review comments or requested changes, merging or enqueueing anything itself, and any notification beyond the tile turning green.

## Folders

The sidebar is a partition: every workspace sits in exactly one folder, and `folder: None` *is* the **Default** folder — deliberately not a `Folder` at all, which is what makes it always present, unnameable, and impossible to delete or drag off the top. Folders are flat and inert: membership decides where a row is drawn and nothing else. Create none and the sidebar looks exactly as it did before they existed — headers appear only once a real folder does.

They replaced an `archived_at` marker that was the same idea wearing behaviour it didn't need. Archiving used to mute "your turn" notifications and drop the row from keyboard navigation; neither survived, so a workspace in a folder named Archived pings like any other. `Store::load` migrates any `archived_at` still in the file into an ordinary (collapsed) folder called "Archived", reading it off a `serde_json::Value` rather than the struct so `Workspace` carries no trace of the retired concept. The first flush without the field ends the migration for good.

Ordering is two Vecs — `AppState.folders` and the existing `AppState.workspaces`. Rendering re-groups the flat workspace order by folder, so only *relative* order within a folder can be observed; the drag handler leans on that, which is why its index math doesn't bother producing a globally tidy list.

Drag does all the moving. Headers drag to reorder folders; a workspace drops between rows or onto a header, where it appends — the only target a collapsed or empty folder can offer. A parent drags with its children nested under it, and the children themselves can't be grabbed, so dragging can't split a family across folders. Deleting a folder sends its contents to Default rather than refusing or destroying anything. `move_workspaces_to_folder` and `reorder_folders` emit no events, for the same reason `reorder_workspaces` doesn't: the sidebar has already drawn the result. Folders are only ever written from the UI, so `App` mirrors each mutation into local state instead of round-tripping.

Deliberately absent: nesting, multi-membership, any agent-facing folder argument (a handoff inherits the caller's folder, like the binary), and any per-folder behaviour at all — including a rollup badge on a collapsed header, so a session wanting attention inside one is genuinely out of sight.

## Children

A handoff made with `as_child` is a **child** of the workspace that asked for it: the sidebar draws it inset beneath its parent, joined by an elbow, and when Ryan deletes it the parent's session is **told**. That's the whole feature, and it exists for one workflow — an agent working through a list, handing each item to a workspace of its own and moving on as each one is finished.

The link is `parent: Option<WorkspaceId>` on `Workspace`, set once at handoff and never changed: there is no UI for making, re-pointing or cutting it. It's separate from `Origin` on purpose — a plain handoff has the same origin as a child, and origin is history, never acted on. Nesting goes to any depth, but a workspace hears only about its *direct* children. `workspaceTree` (`src/workspaceDerived.ts`) nests a row only when its parent is among the rows drawn with it, so a child whose parent is soft-deleted or gone draws at top level without a field changing. Children sit oldest first. They aren't draggable; dragging the parent carries them, which is also what keeps a family in one folder, since a child starts in its parent's folder like any handoff. The field is cleared only where the id stops existing: purge and `forget_workspace` (`orphan_children_of`).

**A parent can't be deleted while it has live children** — `delete_workspace` refuses with `HasChildren`, and the context menu's Delete is disabled with the count. Soft-deleted children don't count, so once the last child is deleted the parent can go without waiting out anyone's grace window.

The event is the child's **soft delete** — the moment Ryan said it's done — not its purge. It names the branch and every PR the child tracked *or had detached*, since clearing a chip doesn't make the PR irrelevant to whoever handed the work out, each with its state fetched fresh (`child_events.rs`): a detached PR isn't polled, and "merged" is exactly what tends to change after a detach. A fetch that fails falls back to the last status seen, then to "state unknown". Undoing the delete sends nothing.

Delivery uses Claude Code's own **cross-session inbox** (`session_inbox.rs`, shared with Shipping's Nudges). Every Claude session binds a Unix socket and exports `CLAUDE_CODE_MESSAGING_SOCKET` and `_TOKEN` to its hooks; `tethys-hook` forwards both, and `handle_session_start` stores them as `AgentSessionMeta::inbox` — only there, because the spawn token match is exact, and a `claude` run inside the session shares its cwd but has an inbox of its own. Persisted, because a session reattached after a restart fires no SessionStart. A post is two JSON lines: `{"type":"auth","token":…}`, then `{"type":"user","message":{"role":"user","content":…}}`. The token is what makes Claude treat it as its own child's message and deliver it rather than hold it for approval. An idle session starts a turn with it; a busy one reads it between tool calls, so it never lands in the composer the way typing into the PTY would.

Each event is queued on the parent (`Workspace::pending_messages`, persisted, read from the old `child_events` key) *before* delivery is tried, and leaves the queue only once delivered. If there's no inbox yet, or the post fails, the next replying hook carries it as `additionalContext`. A parent that was closed when its child went has only a dead socket on file, so `handle_session_start` retries delivery the moment it stores the new inbox — the resumed session starts a turn with the news. Returning it from the `SessionStart` hook instead was tried and is wrong: that context lands silently and waits for Ryan's next prompt, so a parent resumed after its children were deleted sat idle. Nothing wakes or resumes a parent just to deliver.

An orchestrating parent can also report **progress** through `mcp__tethys__set_progress` — done out of total, drawn as a full-width bar and `3/7` on a line of its own under its name, cleared with a total of 0. It's whatever the agent says, nothing derived from its children, and the tool's description tells agents to use it only when orchestrating.

Deliberately absent: any other child event (turn ends, PRs, provisioning failures — a parent wanting status can ask), a "restored" event, a `list_children` tool, collapsing a parent's children, session names or any parent↔child messaging channel, and **codex parents**, which aren't told at all — codex has no inbox and its hooks aren't known to carry context, so their events are dropped rather than queued.

## Tracked PRs

A repo link tracks **one list** of PRs (`RepoLink::prs`). The PR for the workspace's own branch is in there like any other; the only thing special about it is that it gets *added* for you.

It used to have a slot of its own, `link.github`, with `attached_prs` beside it — and that split quietly bought the branch PR four behaviours nothing else had: it couldn't be detached, it re-derived itself from the branch every tick, it vanished silently where an attached PR showed "no data", and re-pointing at it was a refresh where re-attaching anything else was an error. Every one of those was an accident of storage rather than a decision, so the list replaced them. `Store::load` folds both old fields in (`migrate_pr_slots`), reading them off a `serde_json::Value` so `RepoLink` carries no trace of the split, and the first flush ends the migration.

The poller's two target kinds are now the whole of the asymmetry, and they're a division of labour rather than of privilege. `TargetKind::Branch` is a *scan*: it selects only `number` and answers "which PR should this link be tracking", which is the automatic equivalent of attaching it by number. `TargetKind::Pr` pulls the full selection and is what every tracked PR is polled with afterwards, no matter how it got there. So a tick is two passes — scan, then fetch anything the scan just started tracking — because attaching by hand fetches before it records, and a PR you just opened shouldn't sit there saying "no data" for 45 seconds when a hand-attached one wouldn't.

Two consequences worth knowing, both of them the point rather than side effects:

- **A scan takes nothing away.** Tracking ends at detach, not at whatever the branch currently points to. Close the PR on your branch and open another, and you get two chips instead of one silently swapped for the other.
- **Detach works on everything**, which is why `untrack` records the number in `dismissed`: a scan runs every tick and would otherwise put the branch's PR straight back, so detaching it would last 45 seconds. Attaching a dismissed number clears it — asking for a PR by name outranks having once said no to it.

Gone with the split: `isReadyToDelete` and its "ready to delete" banner. It asked whether every tracked PR was merged, which was only ever answerable because the branch slot re-derived itself; with tracking that persists, a closed-and-replaced PR would have pinned it false until someone detached the corpse. Nobody was using the banner to decide anything.

## PR stacks

The members of a **`gh stack`** are drawn wrapped in one outline in the workspace's tab strip, base-first, separated by a chevron. Each PR keeps its own tab — the container is the whole of what stacking adds. Ryan builds stacks with `gh stack` (`github/gh-stack`), so Tethys only has to recognize them, never create or restack them.

Membership is GitHub's own, not inferred. `github/gh-stack` makes a stack a real object on GitHub's side, and GraphQL exposes it on `PullRequest` as `stack { number size }` plus `stackEntry { position }` (1 is closest to the base branch) — all added to the poller's `PR_FIELDS` and flattened into one `Option<PrStack>` on `GithubPrStatus`. `parse_stack` needs all three numbers or yields `None`: a stack we can't place the PR within groups chips it can't order.

Chaining PRs by base branch instead was the obvious cheaper route and is wrong. A hand-made chain and a `gh stack` are indistinguishable from `baseRefName` alone, and only one of them is a thing you can `gh stack sync` — so grouping on bases would put an outline around PRs that have no stack to manage. Nothing fetches `baseRefName`.

`prGroups` (`src/workspaceDerived.ts`) partitions a link's PRs by stack number, ordering each group by `position`, and hands back every PR exactly once with non-stacked ones as groups of one — so the tab strip renders groups uniformly and a workspace with no stack looks exactly as it did before. Every PR the link tracks feeds in, however it got there, since a stack's other branches are ones you attached by hand from this workspace's point of view. Stack numbers are per repository and a link is one repo, so nothing can pull two repos' PRs into one group.

A group is often *smaller* than `stack.size`: six stacked branches with one checked out here is one chip. That case still gets the outline — the PR is genuinely stacked and a bare chip would hide it — plus a `3 of 6` marker, which is the only thing distinguishing "this is the stack" from "this is what I have of it". The number is the tracked PRs' *positions* (`2, 3 of 6` when there are several), not how many are tracked: it used to be the count, and a lone top-of-stack PR read `1 of 2`, which looks like a position and is the wrong one.

Deliberately absent: no stacks in the sidebar (it keeps its flat chip list, so a stack is only visible once you open the workspace), no rollup of the stack's CI or review state onto the container, no `gh stack` invocation of any kind, no fetching the stack-mates the workspace doesn't already track, and no link between a stack and child nesting — separate ideas that happen to look similar.

## Workspace tabs

A ready workspace's detail pane is a strip of **tabs** (`WorkspaceTabs.tsx`): **Chat** (the session's terminal), one per tracked **PR**, and one per **Artifact**. An artifact is something a session produced that Tethys can show rather than leave as terminal text — a **Diagram** (mermaid source), a **Page** (an HTML file) or a **Review** (an ummon review). PRs and artifacts used to be tabs in the side panel, beside the terminal; making them top-level gives each the full pane, and moving the PR chips into their tabs freed the header row they sat in, along with its "+ PR" button.

The terminal stays mounted on every tab, hidden with `visibility` rather than unmounted, so switching tabs never resizes the tmux pane; its input is blurred while hidden so keystrokes can't reach it unseen. The selected tab is remembered per workspace in memory and falls back to Chat when its tab goes away. Chat shows a dot while the session waits on you and another tab is selected.

**Notes** are the only thing left in the **Side Panel** (`SidePanel.tsx`), and it shows only on the Chat tab. Collapsed, it's a 28px rail that is itself the button, with a dot when the workspace has notes. Collapsed state and width are per workspace (id-keyed JSON maps in `localStorage`); an untouched workspace starts collapsed.

A **PR tab** shows the live, logged-in github.com page for that PR. GitHub sends `frame-ancestors 'none'`, so it can't be an iframe like a Page; it's a **native child webview** (`pr_view.rs`, Tauri's `unstable` multi-webview feature) floated over the tab body. That has consequences the rest of the UI has to live with: the frontend owns the geometry (`PrView` measures its host and sends the rect on every layout change, offset in Rust by where the main webview sits under the title bar); it sits above every DOM layer, so a dialog's backdrop or a context menu can't cover it and `PrView` hides it for as long as any `.modal-backdrop` is in the document or a `.context-menu` overlaps it; and `capabilities/default.json` is scoped to the `main` webview so the GitHub page holds no plugin permissions — though app commands aren't ACL-gated, so the real safeguard is only ever loading GitHub. Each PR URL gets its own webview, hidden rather than renavigated on tab switch so the page and scroll position survive, with a small LRU cap (`MAX_LIVE`) because each is a WebContent process. Login is the webview's own persistent cookie store, shared across workspaces and restarts; it cannot inherit Chrome's. The chip in the tab still opens the PR in the default browser, and so does any link inside the page that leaves the PR — a page-side click handler is needed for that because GitHub's Turbo links never reach the navigation handler; GitHub's own sign-in paths and all real navigations (redirects, SSO) stay in the tab.

Artifacts come from **hooks, not from the screen** (`artifacts.rs`). Scraping xterm's buffer was the obvious route and is the wrong one: Claude's renderer uses the alternate screen, so only the visible fraction of a diagram is ever in the buffer, long lines wrap, and a half-streamed diagram is a parse error on every keystroke. The `Stop` hook already carries `last_assistant_message` — the exact markdown, complete — so a Diagram is a fence scan over that. A Page is `PostToolUse` for `Write`/`Edit`/`MultiEdit` on a `.html` path, *or* a Bash command that `open`s one — `tethys-hook` forwards `tool_name`, `tool_file_path` and `tool_command` for this, the only fields of any tool's input Tethys reads. The Bash case is there because the very first page a session made for this was a heredoc, invisible to the file tools; `/show-me` ends every page with `open path/to/show-me-*.html`, so that's the signal that catches the file however it was written. A sandboxed session can't `open` anything, so the same `open` is also read off a `PostToolUseFailure`, and off the final message when the session asks Ryan to run it instead ("! open /path/page.html") — only a path right after the word `open`, so merely naming an `.html` file is not a page. Relative paths resolve against the hook's `cwd`, and every page path is canonicalized so the `Write` and the `open` of one file are one tab. All of these reuse the session→workspace correlation the turn tracker uses (`resolve_session`), so a page a subagent writes lands on its parent's workspace for free.

A **Review** is read off a tool's *output*: ummon prints `ummon is reviewing <repo> at <url>` once it has registered a repo with its local server, so `tethys-hook` forwards the last 8KB of a tool's stdout and Tethys looks for that line on `PostToolUse` — every one of them, since a single command can register several repos. The repo must be under the workspace root and the URL on localhost. The tab iframes ummon's own page without a sandbox, because the page posts to its server and the server checks the request's origin.

Two limits worth knowing. `last_assistant_message` is only the turn's *final* text block, so a diagram drawn before a tool call in the same turn is missed — `record_diagrams` logs at debug on a Stop with no fences, which is how we'd learn that matters. And a Page or Review must resolve under the workspace root (`reconcile::is_under`), so a write to `/tmp` or another checkout can't put a tab in this workspace; an `.html` written via a heredoc and never `open`ed is invisible.

Seeing the same thing again is a **bump, not a new tab**: same page path, review URL or identical diagram source moves the existing artifact to the newest position and increments `revision`, which is what the iframes are keyed on so a re-edited page or a re-run review reloads in place. Artifacts live on `Workspace::artifacts` and so persist in `state.json` — they started out in memory, and the first design session that spanned a restart showed why that was wrong. The cap of 12 per workspace, oldest evicted, is what keeps the file from becoming a graveyard; `Store::load` also drops any Page whose file has gone. Writes go through `update_workspace_quiet`, because `artifact:changed` is the tab strip's own signal — it carries which artifact to select, and doesn't make the sidebar refetch every workspace. A fresh artifact for the workspace you're looking at selects its tab, because a `/show-me` turn is one where you want the screen taken; arrivals for other workspaces just accumulate. Tab labels for a Diagram come from a `title` in the source, else the heading or `**bold**` lead-in just above the fence, else the diagram keyword — cheap heuristics whose fallback is dull rather than wrong. A Review is labelled with its repo's folder name.

Pages render in a sandboxed iframe (`allow-scripts`, no `allow-same-origin`) over Tauri's asset protocol, which is enabled with an *empty* static scope and opened at boot to `worktree_root` only (`lib.rs`), since that's runtime config from `repos.toml`. "Open in browser" goes through a Rust command rather than plugin-opener's `openPath`, which is scope-gated to paths fixed in the capability file. `mermaid` is a couple of megabytes and is imported on first use; a diagram that doesn't parse shows its source and the parser's complaint rather than nothing.

Deliberately absent: keyboard shortcuts, close-all, zoom/pan on diagrams, filtering by session, reading the transcript for earlier text blocks, a way to attach a PR from the UI, and an `open` shim on the session's `PATH` — feasible, since Tethys owns the spawn env, but it would shadow a system command for every subprocess in the session to save the browser tab the hook already lets us observe.

## Logging & diagnostics

Two log sinks, filtered independently (`logging.rs`):

- **File** — `logs/tethys.log.<date>`, full `info,tethys_lib=debug`. This is the real log.
- **stderr** — mirrored into whichever terminal ran `pnpm tauri dev`. Defaults to `warn` only, because it's an unbounded pipe into a terminal emulator's scrollback. `TETHYS_LOG_STDERR` overrides it (`off` to silence, `info,tethys_lib=debug` for the full firehose). `RUST_LOG` sets overall verbosity and caps *both* sinks — raising `TETHYS_LOG_STDERR` past it does nothing.

### Memory watchdog

`scripts/memwatch.sh` samples system + per-app memory every 20s into `~/memwatch/samples.tsv`, and dumps `~/memwatch/snap-<ts>.txt` when a threshold trips. **Tethys launches it at boot** (`memwatch.rs`) — it was never running when a hang happened otherwise. `TETHYS_MEMWATCH=off` disables it, an integer overrides the interval. `~/.local/bin/memwatch.sh` is a symlink to the repo copy.

Tethys owns only the *start*. The script is a singleton on a pidfile, and detaches into a subshell ignoring `SIGHUP`/`SIGINT`, so it survives both the `pnpm tauri dev` that launched it and Tethys itself — Tethys is one of the suspects, and a watchdog that dies with the suspect cannot record the aftermath. Stop it with `pkill -f memwatch.sh`.

Memory is **`phys_footprint`** — the number Activity Monitor shows — read from one `top -l 1` per sample and joined against `ps` for full argv, so every column in a row describes one instant. The original script used `ps rss`, which excludes compressed and swapped pages and so understates by 2-3x *exactly* under the pressure worth catching.

Columns worth knowing: `claude_mb` counts the session processes, `claude_kids_mb` everything they spawned (test runners — the thing usually costing the memory); `tethys_mb` is the Rust binary tree, `webview_mb` the `WebKit.WebContent` process where a Tauri app's UI memory actually lives, `devstack_mb` the `pnpm tauri dev` tree minus Tethys; `dockervm_mb` catches `docker compose` test runs, which land in a VM descended from no session. Trips are on *system pressure* — any single process >8GB, swap >12GB, free <250MB — not on a named app.

The pre-2026-08-31 findings below came from the RSS-based script and understate every figure. Treat the iTerm2 line as unproven rather than settled: it was measured with the wrong instrument.

- **iTerm2 was never the problem** — max 225MB, mean 111MB (RSS; footprint measures ~280MB idle).
- **Tethys is not a heavy process** — mean 66MB, and its stderr output measured ~236 KB/hour before the `warn` default landed.
- **The machine is chronically oversubscribed** on 24GB: swap mean 7.1GB / max 13.3GB, compressor mean 7GB, free pages routinely <100MB. Chrome is the largest consumer (mean 4.0GB, max 7.2GB).
- **The one trip was VS Code**, 5.3GB at 2026-08-14T14:42, alongside `oxlint --lsp` in a Tethys worktree. Each worktree is a full checkout with its own `node_modules`, so opening several in VS Code multiplies the LSP/TS-server stack with nothing shared.

First minute of the rewritten script contradicts the "nothing here is big" reading: `claude_kids_mb` hit 11.2GB while `dockervm_mb` sat at 6.8GB and Chrome at 6.4GB — ~30GB of footprint on a 24GB machine. Sessions running test suites are a live suspect; check `claude_kids_mb` and `dockervm_mb` before blaming Tethys.
